# W01 - 调用栈讲解（标准答案 + 逐帧注解）

> 来源：`code/warmups/wordcount/WordCountStack.java`（探针版）在你机器上的真实运行输出，非理论推演。
> **读栈规则**：栈是从"当前正在执行的代码"（最上面）到"线程起点"（最下面）的路径。读栈 = 从自己的 lambda 往上爬，看谁调用了谁。

---

## 一、SUBMIT 侧：`env.execute()` 进行中，main 线程在干嘛？

```
main → WordCountStack.main
     → StreamExecutionEnvironment.execute(1846)
     → LocalStreamEnvironment.execute(68)
     → StreamExecutionEnvironment.execute(1878)
     → CompletableFuture.get()
     → LockSupport.park()          ← main 线程停在这里"睡觉"
```

**人话**：main 线程此刻**没有在算任何数据**。它已经把作业（DAG）构建完、提交给了本地集群（LocalStreamEnvironment = 进程内 mini-cluster），然后阻塞在一个 Future 上**等作业跑完**。`park()` = 线程挂起，不占 CPU。

---

## 二、EXEC 侧：reduce lambda 执行的那一刻，是谁在跑？

**线程名**：`Keyed Reduce -> Sink: Print to Std. Out (7/8)#0` ——**不是 main！** 是集群另起的一条任务线程。

从栈底（线程起点）往上读，每一帧的人话：

| 帧（从底往上） | 人话 |
|---|---|
| `Thread.run` → `Task.run / doRun / restoreAndInvoke` | `Task` 是 **flink-runtime** 包的类 = TaskManager 里一条"子任务"的容器，线程的真正起点 |
| `StreamTask.invoke` → `runMailboxLoop` → `MailboxProcessor.runMailboxLoop` | StreamTask 用"邮箱循环"驱动执行：每轮从邮箱取一个动作（处理数据 / checkpoint / 定时器）执行 |
| `StreamTask.processInput` → `StreamOneInputProcessor.processInput` | 本轮邮箱动作 = "处理一批输入数据" |
| `AbstractStreamTaskNetworkInput.emitNext` → `processElement` | 从网络层取下一条记录 |
| `OneInputStreamTask$StreamTaskNetworkOutput.emitRecord` | 把记录递给算子链 |
| `StreamGroupedReduceOperator.processElement` | 你的 reduce 被包在这个算子里：按 key 取出上次结果 → 调你的 lambda → 存回 keyed 状态 |
| `wordcount.WordCountStack.lambda$main$...` | **你的代码**，每次一条记录触发一次 |

**三个关键发现**：

1. **同一进程、不同线程**：main 线程在 park 等结果，数据在任务线程（`Task.run` 那条世界线）里流动。你在 IDEA 里看到的就是这两条线。
2. **线程名暴露了 operator chain**：`Keyed Reduce -> Sink: Print` 连成一个 task——`reduce` 和 `print` 没有网络传输，直接链在一起（这正是 W2 要学的 chain 在运行时的样子）。`keyBy` 不出现在名字里——它不是算子，是"按 key 重新分区 + 启用 keyed 状态"的语义。
3. **`(7/8)#0`** 是并行子任务编号——你的 3 条字符串被分成了 8 个并行度的子任务。

## 三、三个预测问题的实际答案（现在才揭晓）

- **Q1（调用栈经过哪些类回到 main()？）**：执行栈**不回到 main()**。执行栈的底是 `Task.run`（新线程的起点），main 只是"作业的提交者"。预测里如果写过"从 reduce 回到 main()"——这就是今天最重要的分岔：**提交世界线和数据世界线是两条栈**。
- **Q2（execute() 时发生了什么？）**：构建 DAG（StreamGraph）→ 提交给本地 MiniCluster → main 阻塞在 Future 上等完成。数据在此刻刚开始流动。
- **Q3（keyBy 那行执行时数据存在吗？）**：`keyBy` 那行代码在 main 里执行过**一次**（构建 DAG 时，那时没有数据），之后**永远不再执行**。在 `keyBy(...)` 这行打断点只会在提交期停一次；真正每条数据都触发的是 key selector lambda 和算子（reduce）的代码——在任务线程里。
